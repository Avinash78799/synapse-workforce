============================================================
1. PRODUCT VISION
============================================================

Working concept:

A modular AI workforce platform where businesses can deploy specialized AI agents that understand goals, execute real work through business systems, operate within defined permissions, verify their actions, escalate when necessary, and continuously report measurable outcomes.

This is NOT:
- A chatbot
- A ChatGPT clone
- A generic AI assistant
- Merely an agent builder
- A collection of prompts
- A multi-agent demo

It is an AI workforce infrastructure + specialized business agents platform.

Long-term vision:

AI Assistant
    ->
AI Worker
    ->
AI Team
    ->
AI Workforce
    ->
AI Workforce Platform

The platform should eventually allow a company to activate specialized workers such as:
- Operations Agent
- Customer Support Agent
- Sales Agent
- Finance Agent
- HR Agent
- IT Agent
- Procurement Agent
- Compliance Agent

Important:
The first release focuses on two strong agents. Do not build many weak agents.

============================================================

Each agent has its own:
- Goals
- Workflows
- Memory
- Context
- Skills
- Tools
- Policies
- Permissions
- Evaluations
- Configuration
- Versioning
- Audit scope

Tenant
    |
    +-- Operations Agent
    |      +-- Own memory
    |      +-- Own policies
    |      +-- Own skills
    |      +-- Own tools
    |      +-- Own workflows
    |      +-- Own permissions
    |
    +-- Support Agent
           +-- Own memory
           +-- Own policies
           +-- Own skills
           +-- Own tools
           +-- Own workflows
           +-- Own permissions

A client can:
- Use only Operations
- Use only Support
- Use both

There must be NO automatic sharing of:
- Business context
- Memory
- Workflows
- Data
- Credentials
- Permissions

If both agents need to communicate later, communication must happen through an explicit, authorized and auditable interface.

This isolation prevents:
- Data leakage
- Permission confusion
- Cross-agent contamination
- Unpredictable behavior
- Unnecessary coupling

============================================================

The LLM must NOT be the final authority on dangerous actions.

Use a deterministic policy layer outside the model.

Example:

    ->

    ->

    YES

    YES
Refund reason allowed?
    YES
    ->
EXECUTE

High-risk example:

Refund Rs. 75,000
    ->
Policy Engine
    ->
High-risk action
    ->
Human Approval
    ->
Approved?
    ->
Execute

Prohibited example:

Delete customer account
    ->
Policy Engine
    ->

Policies should be:
- Deterministic
- Versioned
- Auditable
- Testable
- Agent-specific
- Tenant-specific where required

GAP CLOSED (v1.1) - APPROVAL ENGINE DETAIL:
The blueprint says "human approval" but never defines the mechanics. Needed:
- Who is a valid approver for a given risk level/amount (named role, not just
  "a human")
- Timeout: how long a request waits before it expires, and whether expiry
  means default-deny or auto-escalate
- Which policy VERSION applies if the policy changes while a request is
  pending (pin the version at request-creation time)
- Notification path (email/Slack/dashboard) so "pending approval" doesn't
  silently stall a run indefinitely


============================================================
10. RISK-BASED AUTONOMY
============================================================

Do not use only "autonomous" vs "not autonomous."

Use autonomy levels.

LEVEL 0 - OBSERVE
Agent can inspect information.

LEVEL 1 - RECOMMEND
Agent analyzes and suggests actions.

LEVEL 2 - PREPARE
Agent prepares actions but does not execute.

LEVEL 3 - APPROVAL
Agent prepares action -> human approves -> execution.

LEVEL 4 - CONTROLLED AUTONOMY
Agent automatically executes predefined low-risk actions.

LEVEL 5 - WORKFLOW AUTONOMY
Agent can execute larger predefined workflows within strict boundaries.

Autonomy should be configurable per:
- Agent
- Skill
- Tool
- Action
- Tenant
- Risk level

GAP CLOSED (v1.1) - AUTONOMY PROMOTION CRITERIA:
"Confidence-aware autonomy" is listed later as a differentiator (Section 39)
but nothing defines what promotes an action from one level to the next.
Define, per action type, a concrete promotion rule before Phase 8, e.g.:
minimum N simulated/production occurrences, minimum success rate over a
trailing window, zero unauthorized-action incidents, and a required manual
sign-off to move up a level. Without this, "Level 3 -> Level 4" stays a
subjective call with no audit trail behind it.

11. VERIFICATION SYSTEM
============================================================

An agent saying:
"Refund completed."

is not sufficient.

The platform must verify important actions.

Example:

Execute refund
    ->
Payment provider
    ->
Check transaction state
    ->
Refund confirmed?
    ->
YES
    ->
Update ticket
    ->
Notify customer

If verification fails:

Action completed?
    ->
UNKNOWN
    ->
Retry / Investigate / Escalate

Verification should be implemented wherever practical for:
- Payments
- Refunds
- Orders
- Inventory changes
- Ticket updates
- External API actions
- Workflow completion

GAP CLOSED (v1.1) - IDEMPOTENCY:
"Verify, then retry on failure" is not safe by itself. If a refund call times
out after the provider actually processed it, a naive retry double-refunds.
Every mutating tool call must carry a stable idempotency key derived from the
run/task ID, and the tool/integration layer must be built (or wrapped) to
honor it. Verification failing with UNKNOWN must trigger a status check
against the idempotency key before any retry, never a blind re-execute.

GAP CLOSED (v1.1) - CONCURRENT TRIGGER DEDUPLICATION:
Once agents react to both events and direct requests, the same underlying
case can be triggered twice at once - e.g. a "PaymentFailed" event and a
customer's own support message both start a refund workflow for the same
order. Without a lock/dedup key scoped to the business entity (order ID,
ticket ID), this produces duplicate actions even with per-call idempotency
keys, because the two triggers generate two different keys for the same
real-world case. Add an entity-level lock (or a "case" concept that both
triggers must attach to) before Phase 8.

GAP CLOSED (v1.1) - VECTOR SEARCH TENANT SCOPING:
A pgvector similarity query that omits a tenant_id (and agent_id, per Section
19's isolation rule) filter is the single most common way this kind of system
leaks one customer's SOPs/refund policy into another tenant's agent context.
Every retrieval call must filter by tenant_id and agent scope BEFORE the
similarity search, not after, and this should have a dedicated test in the
security test suite (Section 36's tests/security/).

27. SECURITY ARCHITECTURE
============================================================

TENANT ISOLATION

CREDENTIAL ISOLATION
Each integration has scoped credentials.

TOOL ALLOWLISTING
Agents only see tools they are permitted to use.

SECRETS MANAGEMENT
API keys and secrets never enter prompts.

POLICY ENGINE
High-risk actions require controls.

RATE LIMITS
Prevent runaway execution.

SPEND LIMITS
Prevent runaway model/API costs.

KILL SWITCH
Immediately disable an agent.

GAP CLOSED (v1.2) - KILL SWITCH SEMANTICS:
"Immediately disable" is ambiguous for an agent mid tool-call. Default
behavior: a kill switch blocks the START of any new run and any new plan
step in a running task immediately, but lets an already-dispatched tool call
that mutates external state (a refund already sent to the payment provider)
finish and verify rather than abandoning it mid-flight - an abandoned
in-flight mutation is harder to reconcile than one more action. A separate,
explicitly-labeled "hard abort" exists for security incidents (e.g. a
compromised credential) where even in-flight calls must be cut regardless of
reconciliation cost. Both are logged to the audit system with the reason.

AUDIT
Critical actions are logged.

Additional future enterprise controls:
- Encryption
- Data residency
- BYOK
- Retention policies
- Deletion policies
- SSO
- Advanced RBAC

GAP CLOSED (v1.1) - THREE ITEMS THAT SHOULD NOT WAIT FOR "FUTURE":

1. TENANT ISOLATION MECHANISM
   "Customer A cannot access Customer B data" is a goal, not a mechanism. A
   single shared PostgreSQL instance (per Section 34/35) enforced only by
   application-layer WHERE clauses is one missed filter away from a
   cross-tenant leak. Use Postgres Row-Level Security (RLS) policies keyed
   on tenant_id as the enforced boundary, with application-layer filtering
   as a second layer, not the only layer. Build this in Phase 4, not later.

2. SECRETS STORAGE
   The DATABASE MODEL (Section 34) lists a `credentials` table alongside
   ordinary business tables. Integration credentials (payment provider keys,
   email/Slack tokens) should live in a dedicated secrets manager (e.g.
   Vault, AWS/GCP KMS) with the Postgres table holding only a reference/
   pointer, not the secret itself.

3. PAYMENT DATA SCOPE
   The Operations and Support agents both touch payments and refunds from
   Day 1 of the simulation, and V2 adds real Razorpay/Stripe integration.
   Decide PCI-DSS scope now: the platform should never store or pass raw
   card numbers through the agent/tool layer - only tokenized references
   from the payment provider. Retrofitting this after integrations exist is
   far more expensive than deciding it up front.

37. DEVELOPMENT ROADMAP
============================================================

PHASE 0 - FOUNDATION

Build:
- Repository
- Frontend
- FastAPI backend
- PostgreSQL
- Authentication
- Tenant model
- Agent model
- Basic APIs
- Database migrations
- Logging

Goal:
Platform skeleton.


PHASE 1 - AGENT CORE + GOVERNANCE STUB (was contradicted by Section 45; fixed in v1.1)

Build:
- Model abstraction
- Agent runtime
- Task state
- Tool interface
- Planning
- Execution
- Retries
- Error handling
- Context
- Basic memory
- Run tracking
- MINIMAL policy engine (allow/deny/require-approval per tool, even if rules are hardcoded)
- MINIMAL approval engine (a request can be created, approved, denied)
- Idempotency keys on every tool call that mutates state
- Basic audit log (who/what/when/result) - do not defer this to Phase 4

Goal:
One generic agent can reliably perform controlled tasks, and no tool call is
ever executed without passing through a policy check and an idempotency key,
even in simulation. This is a correction from v1.0: Section 45's development
principle (Core -> Tools -> Policy -> Execution) contradicted the old Phase 2/3
plan, which built Operations and Support agents executing real actions with no
policy engine, no approval engine, and no audit trail until Phase 4. Building
"do whatever the plan says" execution habits first and retrofitting guardrails
later is a common source of bypassed policy checks and undertested approval
paths. The full RBAC/tenant-isolation/kill-switch buildout still happens in
Phase 4 below - only the minimal enforcement hooks move earlier.


PHASE 2 - OPERATIONS AGENT

Build:
- Acme Commerce simulator
- Orders
- Payments
- Inventory
- Shipments
- Operational events
- Operations skills
- Workflows
- Reporting
- Escalation
- Every mutating action routed through the Phase 1 policy/approval stub

Goal:
Operations Agent performs a complete operational workflow, already gated by
policy and approval from day one.


PHASE 3 - SUPPORT AGENT

Build:
- Customer lookup
- Order lookup
- Ticket system
- Payment investigation

- Escalation
- Duplicate-request lock: a customer message and an independent event
  (e.g. a webhook retry) must not be able to trigger the same refund twice

Goal:
Support Agent independently resolves customer cases.


PHASE 4 - GOVERNANCE HARDENING

Build:
- Agent identity
- RBAC
- Tool permissions
- Policy engine versioning (policies referenced by version in every audit row)
- Approval engine: timeouts, default-deny on expiry, named approver roles
- Risk levels
- Audit logs
- Kill switch (define: does it drain in-flight tool calls or hard-abort them?)
- Tenant isolation enforced at the database layer (Postgres Row-Level
  Security), not only in application code
- Secrets manager (Vault/KMS-backed) for credentials, not a plain
  `credentials` table

Goal:
Upgrade the Phase 1 governance stub into enterprise-grade controls, without
having let agents run ungoverned in the meantime.

47. CHANGELOG v1.1 - GAPS FOUND AND FIXED
============================================================

This pass reviewed the plan end-to-end for internal contradictions and
operational failure modes. Fixes are inlined at the relevant section above
(each marked "GAP CLOSED (v1.1)"); this is the index.

1. PHASE-ORDER CONTRADICTION (Section 37 vs 45)
   Section 45's build order puts the Policy Engine before Agents; the old
   Phase 2/3 built both agents executing real actions before Phase 4 built
   governance at all. Fixed by moving a minimal policy/approval/audit/
   idempotency stub into Phase 1, so no action - even in simulation - is
   ever executed ungoverned.

2. IDEMPOTENCY (Section 11)
   No mechanism existed to prevent a retried tool call (e.g. after a
   timeout) from double-executing a refund. Added idempotency-key
   requirement on every mutating tool call.

3. CONCURRENT-TRIGGER DEDUPLICATION (Section 13)
   Event-driven and human-triggered workflows can independently start the
   same real-world case (e.g. a refund) with different idempotency keys,
   duplicating the action even with per-call idempotency in place. Added an
   entity-level lock requirement.

4. APPROVAL ENGINE MECHANICS (Section 9)
   "Human approval" had no defined approver role, timeout, expiry behavior,
   or policy-version pinning for in-flight requests. Specified all four.

5. AUTONOMY PROMOTION CRITERIA (Section 10)
   "Confidence-aware autonomy" was named as a differentiator (Section 39)
   but never defined. Added concrete promotion rule (trailing success rate,
   sample size, zero unauthorized-action incidents, manual sign-off).

6. VECTOR SEARCH TENANT SCOPING (Section 20)
   pgvector retrieval must filter by tenant_id/agent scope before the
   similarity search, called out explicitly with a required security test.

7. TENANT ISOLATION MECHANISM (Section 27)
   "Isolated" was a goal without a mechanism on a shared Postgres instance.
   Added Row-Level Security as the enforced boundary, not just app-layer
   filtering.

8. SECRETS STORAGE (Section 27, 34)
   The `credentials` table in the data model would otherwise hold secrets
   directly in Postgres. Redirected to a dedicated secrets manager with
   Postgres holding only a reference.

9. PAYMENT DATA / PCI SCOPE (Section 27)
   Refunds and payments are handled from Day 1 with real providers arriving
   in V2, but card-data handling scope was never decided. Specified
   tokenization-only, no raw card data through the agent/tool layer.

Not changed in v1.1, closed in v1.2 (see Section 48).


============================================================
48. CHANGELOG v1.2 - FINALIZATION
============================================================

This pass closed every item v1.1 had left open, and fixed one remaining
internal inconsistency. Nothing is deferred to "decide later" anymore.

1. KILL SWITCH SEMANTICS (Section 27)
   Left undefined in v1.1. Now specified: default is graceful drain (block
   new runs/steps, let already-dispatched external mutations finish and
   verify); a separate labeled "hard abort" exists for security incidents.

2. FRAUD / ABUSE SIGNAL (Section 3, Section 14)
   Left uncovered in v1.1. Added AbuseSignalSkill to the Support Agent:
   repeated duplicate-charge claims from the same customer/order route to
   approval instead of auto-executing every time, independent of amount.

3. V1/V2 SCOPE INCONSISTENCY (Section 44)
   The scope lock listed "Approvals" under V2, while Section 37's Phase 1/4
   build the policy and approval engine well before Phase 7 (Real
   Integrations, the actual start of V2). Fixed: the approval engine now
   explicitly appears under V1 PLATFORM; the V2 line is reworded to what
   actually belongs there - multi-channel approval routing (Slack/email)
   once real external integrations exist.

4. V1 SCOPE LOCK DIDN'T MENTION ITS OWN REQUIREMENTS (Section 44)
   Idempotency keys, Postgres Row-Level Security, and the secrets manager
   were added to Phases 1 and 4 in v1.1 but never made it into the V1 SCOPE
   LOCK summary, so a reader skimming Section 44 alone would miss them.
   Added explicitly.

The plan is now internally consistent end to end: every mechanism named as
a differentiator or a phase deliverable is also defined with who owns it,
when it's built, and what happens at its failure edge (timeout, retry,
concurrent trigger, kill).
